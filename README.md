# 篮球正负值复核（FastAPI + SQLite）

同节同秒的换人与得分可能交错发生，导致球员正负值不唯一。本应用上传一场比赛的
**换人 CSV**、**得分 CSV** 与**本方首发五人**，计算每名本方球员正负值（在场时
本方得分 − 对方得分）的**可达最小值 / 最大值**；看录像后可在网页登记同节同秒的
一笔换人和一笔得分谁先发生，系统计入提交时已生效的全部核实后重算，并把核实记录
与重算结果一并写入 SQLite。

## 目录结构

```
app/
  engine.py     # 核心引擎：时刻分组 + 组内滚动动态规划求正负值区间
  csvio.py      # CSV 解析与上传校验（保留两表原始行序）
  database.py   # SQLite 持久化、写锁串行化、锁等待重试
  main.py       # FastAPI 路由
  static/       # 原生 HTML/JS/CSS 页面（无构建步骤）
samples/        # 可直接在网页试用的样例 CSV（基本 / 高密度 / 录像核实）
scripts/
  bench_memory.py  # 同秒组求解峰值内存基准（换人/得分/球员同步增长）
  demo_flow.py     # 通过 HTTP 复现上传、核实、无解登记全流程
tests/          # pytest：引擎单测 + API/并发集成测试（37 个用例）
Dockerfile
docker-compose.yml
```

## CSV 格式

换人 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` | 节次（从 1 开始） |
| `remaining` | 该节剩余秒数 |
| `outgoing` | 下场球员 |
| `incoming` | 上场球员 |

得分 CSV（表头固定）：

| 列 | 含义 |
| --- | --- |
| `period` / `remaining` | 节次 / 剩余秒数 |
| `team` | `own`/`opp`（也接受中文 `本方`/`对方`） |
| `points` | 分值，1、2 或 3 |
| `scorer` | 本方得分必填得分者；对方得分留空 |

两表各自必须按比赛进程排列（节次递增、同节剩余秒数不增），同节同秒的记录在表内
保持原始行序；上传时若发现时刻倒退直接拒绝，不做自动重排。

## 计算模型

1. **时刻分组**：所有事件按 `(节次, 剩余秒数)` 分组，时刻之间顺序固定；同组内
   换人之间、得分之间分别保持各自 CSV 行序，换人与得分可以任意交错。
2. **组合法性**：
   * 换人执行时，下场球员必须在场、上场球员必须在场外（与交错无关，静态检查）；
   * 本方得分执行时，得分者必须在场；对方得分无得分者要求；
   * 核实记录给同组内一对（换人，得分）附加确定的先后边。
3. **滚动动态规划**：组内以 `(已执行换人数 i, 已执行得分数 j)` 为状态，场上阵容
   只由 `i` 决定。核实边先压缩成「执行第 i 笔换人前至少完成 `score_need[i]` 笔
   得分」与对称的 `sub_need[j]`。
   * 数顺序：按 `total = i + j` 逐层滚动，只保留当前层与下一层的一维数组
     （长度 ≤ `min(换人数, 得分数) + 1`）。
   * 求区间：不再为每个状态存「全体球员的 min/max 向量」，而是**逐名球员**跑一次
     同样的滚动 DP，求他自己累计增量的区间；在场轨迹相同的球员共享一次计算。
     因此单组的额外工作内存只与**换人 + 得分 + 核实 + 球员**的总数成线性关系。
   * 顺序数上限仍为 1000 万（超出截断）；截断只影响显示计数，**每名球员的区间
     仍精确**（区间与顺序数分属两次 DP，互不依赖）。
4. **无解处理**：若数据本身或新增核实后排不出合法顺序，接口返回 400/409，说明
   哪一节、哪一秒、哪条原表记录阻塞（`blocking: [{table, row}]`）以及违反的规则；
   核实登记场景下整个事务回滚，已提交的核实与统计保持不变。

## API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/api/games` | 上传名称、首发与两份 CSV，返回首版区间 |
| `GET` | `/api/games` | 比赛列表（含核实数、合法顺序数、状态） |
| `GET` | `/api/games/{id}` | 详情：时间线、核实记录、最新结果 |
| `POST` | `/api/games/{id}/verifications` | 登记一条同秒先后核实并重算（重复提交幂等；冲突返回 409 且回滚） |
| `GET` | `/samples/{filename}` | 样例文件（`subs.csv`、`scores.csv`、`subs_dense.csv`、`scores_dense.csv`、`subs_scorer.csv`、`scores_scorer.csv`） |

无解时 400/409 响应体为 `{"detail": 中文说明, "reason": 中文说明, "period": 节次,
"remaining": 剩余秒数, "blocking": [{"table": "sub"|"score", "row": 原表行号}]}`；
`detail` 保持为字符串以兼容既有调用方。

## 并发与持久化

* 每个 FastAPI 进程内用一把可重入写锁把「插入核实 → 重读全部已生效核实 → 重算 →
  写结果」串行化；每次重算都重新读取当时数据库中**全部**核实记录，因此并发提交
  的效果等价于按某个串行顺序全部生效。
* SQLite 开启 WAL 与 `busy_timeout`，写操作对 `database is locked` 做退避重试，
  多 worker 部署也不会丢提交。
* 表：`games`、`events`、`verifications`、`results`（每比赛一行最新结果）、
  `result_snapshots`（每次有效重算的历史快照，含当时核实数）。

## 本次改动摘要

1. **求解内存线性化**（`app/engine.py`）：去掉「每个状态存全体球员 min/max 向量」
   的做法。数合法顺序与求每名球员区间各用一次滚动层 DP，只保留相邻两层的一维
   数组；同组内在场轨迹相同的球员共享一次计算。单组额外工作内存从
   `O(状态数 × 球员数)` 降为 `O(换人 + 得分 + 核实 + 球员)`。
2. **区间精度不受顺序数上限影响**：顺序数照旧截断在 1000 万，区间由独立 DP
   精确求出；新增用例覆盖「30 换人 + 30 得分、顺序数已达上限」时每名球员仍精确。
3. **无解定位更精确**：`InfeasibleError` 增加 `period` / `remaining` /
   `blocking`（原表行号列表）；上传与核实登记都返回同一结构，400/409 响应中
   `detail` 仍为字符串以兼容旧调用方。核实登记失败时事务整体回滚。
4. **网页演示增强**：三套样例按钮（基础 / 高密度 / 录像核实）、下载链接，
   打开比赛时自动预填核实表单的节次、时刻与行号，错误提示展示位置与阻塞行。
5. **脚本**：`scripts/bench_memory.py` 量化内存；`scripts/demo_flow.py` 通过公开
   HTTP 接口复现上传、核实、无解登记全流程。
6. **测试**：从 30 项增至 37 项，新增内存线性、顺序数上限下区间精度、结构化
   无解响应、样例上传等用例；另做了 4000+ 随机/穷举用例与旧实现的差分核对。

## 实测结果

本地 Python 3.11 + uvicorn 实测（自动化用例见 `tests/`，37 项全部通过）：

* 样例比赛初始共 3 种合法交错，A5 区间 `[-2, 1]`、B1 区间 `[3, 6]`；
  登记「换人 1 先于得分 1」后合法顺序收敛为 1，A5 变为 `[0, 0]`、B1 变为 `[4, 4]`。
* 重复提交同一核实返回 `duplicate=true`，不新增记录。
* 对同一对换人/得分并发登记正反两个方向：一个 200、一个 409，最终核实数与合法
  结果保持一致（冲突事务回滚，旧结果照旧）。
* 三条不同时刻组的核实并发提交：全部 200，快照表记录合法顺序数 8 → 4 → 2 → 1。
* 非法换人（下场者不在场）上传返回 400 并指明行号；CSV 时刻倒退返回 400 且不入库。
* 除此之外，还把新旧引擎在 4000+ 个随机/穷举输入上做了差分核对（单组、多组、
  含核实、含不可行），区间与合法顺序数逐项一致；另有 1312 个用全排列暴力枚举
  的用例逐项比对通过。

### 求解内存对比（同秒组，`scripts/bench_memory.py` 同口径）

构造最坏情况：同秒 `n` 次换人 + `n` 次得分，全部得分由始终在场的 A1 完成，
`tracemalloc` 记录 `_solve_group` 的峰值分配。

| 换人 | 得分 | 球员 | 旧实现峰值 | 新实现峰值 | 新实现耗时 | 降幅 |
| --- | --- | --- | --- | --- | --- | --- |
| 20 | 20 | 14 | 0.81 MiB | 0.029 MiB | 0.05 s | 28× |
| 40 | 40 | 19 | 5.45 MiB | 0.052 MiB | 0.26 s | 104× |
| 80 | 80 | 29 | 21.17 MiB | 0.094 MiB | 1.71 s | 225× |
| 120 | 120 | 39 | 95.74 MiB | 0.142 MiB | 5.31 s | 676× |

新实现峰值随事件数近似线性增长；事件数固定为 40+40、只把球员数从 14 增到 1094
时，峰值仅从 53.6 KiB 升到 97.1 KiB（旧实现该维度不变，因为它本来也只存 5 人在场）。

### 合法顺序上限下的区间精度

同秒 30 换人 + 30 得分：合法顺序远超 1000 万，`total_legal_orders` 截断为
10000000；此时 A1 仍精确为 `[30, 30]`，首个替补 B1 为 `[0, 30]`，最后登场的
B30 为 `[0, 30]`。截断只影响显示计数，不影响区间。

### 无解登记

「录像核实样例」中得分者 B2 要等第 2 笔换人才上场。登记「得分 1 先于换人 1」
后无解，接口返回：

```json
{
  "detail": "第 1 节剩余 600 秒：已合法推进 0 个事件后，其余换人/得分无法继续，核实要求得分 CSV 第 1 行先于换人 CSV 第 1 行，但该得分此前尚未发生；本方得分者 B2（得分 CSV 第 1 行）在该时刻任何已构造的合法顺序中都无法处于场上",
  "period": 1,
  "remaining": 600,
  "blocking": [{"table": "score", "row": 1}, {"table": "sub", "row": 1}]
}
```

核实数保持 0、结果保持原值（整个事务回滚）。

## 待办 / 已知限制

* 运行环境未安装 Docker 守护进程（无 root、无 user namespace），Dockerfile 与
  Compose **未在本机实际构建**；已用官方 Compose Schema 校验 `docker-compose.yml`
  通过，并用 uvicorn 直接运行完成全部实测。首次在有 Docker 的机器上建议先
  `docker compose config` 再 `docker compose up --build`。
* 目前只建模本方球员名单与本方换人；对方阵容、对方换人不影响本方正负值，未入库。
* 未做账号体系与多人编辑权限，所有访问者均可登记核实（适合单队内部复核场景）。
* 新实现按 `O((换人+得分) × min(换人,得分))` 的**时间**规模跑网格 DP；真实比赛
  每组通常个位数，但同秒 100+ 事件的极端数据在大分组下单组耗时可达数秒。
  如需再提速，可改用差分数组或分治卷积，工作内存仍能保持线性。
* 暂无事件级编辑/删除接口，录入错误目前需要重新上传比赛。
